# dueboard

A full-stack app on Cloudflare, built with [Alchemy](https://alchemy.run) and [Effect](https://effect.website):

- **TanStack Start** (React): the frontend, deployed as a Cloudflare Worker plus static assets.
- **Effect RPC**: the API, deployed as a separate, private `Cloudflare.Workers.RpcWorker`.
- **Drizzle + Neon Postgres**: the database, reached through a Cloudflare Hyperdrive connection pool. Migrations are generated on deploy.
- **Atom RPC** (`effect/reactivity/AtomRpc` + `@effect/atom-react`): reactive queries and mutations in the browser.
- **Better Auth** ([`@alchemy.run/better-auth`](https://alchemy.run/better-auth/)): Google sign-in, plus a unique username chosen at `/onboarding`. Each user sees only their own todos.

The app is still a starter todo list for now. The code follows Alchemy's [cloudflare-tanstack-rpc-drizzle example](https://github.com/alchemy-run/alchemy/tree/main/examples/cloudflare-tanstack-rpc-drizzle) ([guide](https://alchemy.run/cloudflare/frontend/full-stack-tanstack-rpc-drizzle/)). It's split into two stacks, following the [monorepo-multi-stack example](https://github.com/alchemy-run/alchemy/tree/main/examples/monorepo-multi-stack).

## Architecture

```
Browser (React)
  │  useAtomValue / useAtomSet
  ▼
AtomRpc client (TodoRpcs)        web/src/rpc-client.ts
  │  HTTP POST /rpc (JSON)
  ▼
TanStack Start worker            web/src/routes/rpc.ts, web/src/routes/api/auth/$.ts
  │  env.API.fetch(...)          (private service binding, across stacks)
  ▼
ApiWorker (RpcWorker)            api/src/api.ts  (/rpc → todo RPCs, /api/auth/* → Better Auth)
  │  Drizzle.Postgres + Better Auth over Hyperdrive
  ▼
Neon Postgres branch             api/src/database.ts
```

The browser can't use a Cloudflare service binding directly. So the `AtomRpc` client calls the same-origin `/rpc` route, and the TanStack Start server forwards each request to the private `ApiWorker`. The API has no public URL, and no CORS setup is needed. Better Auth's routes (`/api/auth/*`) take the same path, so its cookies and the Google callback live on the website's origin.

## Layout

```
.
├── package.json              # workspaces: ["api", "web"]
├── tsconfig.json             # project references to api and web
├── tsconfig.base.json        # shared compiler options
├── api/                      # "DueboardApi" stack
│   ├── alchemy.run.ts        # Neon + ApiWorker
│   ├── migrations/           # generated by Drizzle.Schema on deploy
│   └── src/
│       ├── rpc.ts            # TodoRpcs contract + auth middleware tag (shared with web)
│       ├── schema.ts         # Drizzle `todos` table
│       ├── database.ts       # Neon project/branch + Hyperdrive
│       ├── auth.ts           # Better Auth (Google + username plugin)
│       ├── api.ts            # ApiWorker RpcWorker (handlers, auth routes)
│       └── Stack.ts          # Api stack handle + ApiWorker ref
└── web/                      # "DueboardWeb" stack
    ├── alchemy.run.ts        # Website.Vite with API binding
    ├── vite.config.ts
    └── src/
        ├── env.d.ts          # types env.API for cloudflare:workers
        ├── env.ts            # dev-safe Proxy over the cloudflare:workers env
        ├── rpc-client.ts     # AtomRpc client + query/mutation atoms
        ├── auth-client.ts    # Better Auth browser client
        ├── session.ts        # getSessionUser server function (route guards)
        ├── router.tsx
        ├── routeTree.gen.ts  # generated by TanStack Router
        └── routes/           # __root.tsx, index.tsx (todos), sign-in.tsx, onboarding.tsx,
                              # rpc.ts and api/auth/$.ts (proxies)
```

**How `web` uses `api`:**

- **RPC contract:** the browser imports `TodoRpcs` from `@dueboard/api/rpc`, so both ends share one schema.
- **Service binding:** `web/alchemy.run.ts` passes `ApiWorker` to the Website's `env` as `API`. `ApiWorker` is defined as `Cloudflare.Worker.ref("ApiWorker", { stack: "DueboardApi" })` in `api/src/Stack.ts`. Only the `DueboardApi` stack declares and deploys the Worker; `web` binds to the deployed one for the same stage.

**Stack names:** Alchemy keeps one state store per Cloudflare account, keyed by stack name and stage. The stacks are named `DueboardApi` and `DueboardWeb`, not `Api` and `Web`, so they never share state with another project's stacks on the same account. For the same reason, the rate limit `namespaceId`s (`1003`, `1004`) must not be used by any other Worker on the account.

## Status

- **Deployed:** not yet.
- **Hyperdrive:** enabled (see [Hyperdrive](#hyperdrive)).
- **Database names:** each stage gets a Neon project `dueboard-<stage>`, with the app's data on a branch named after the stage, in a database called `dueboard`. `pr-*` stages put their branch in the `dueboard-staging` project instead.
- **Database region:** the Neon project is in `aws-us-east-1` (Virginia). With Hyperdrive, requests reuse warm connections instead of opening a new one each time. Moving the project closer (e.g. `aws-ap-southeast-1`, Singapore) would cut latency further, but changing the region replaces the Neon project and its data.

## Dependencies and version pins

Every workspace dependency's version lives once, in the `catalog` in the root `package.json`. Workspaces reference it with `"catalog:"`, so `api` and `web` always resolve the same version. To add a package, run `bun add <pkg> --catalog` inside the workspace. To bump one, change it in the catalog and run `bun install`.

The dependencies were added the way the [Alchemy docs](https://alchemy.run) install them, with `--catalog` added:

```bash
# root
bun add -d @types/bun typescript

# api/
bun add alchemy@latest @alchemy.run/cloudflare@latest effect @effect/platform-bun @effect/platform-node --catalog
bun add @alchemy.run/neon@latest --catalog
bun add @alchemy.run/drizzle@latest drizzle-orm@1.0.0-rc.5-ab785fc @effect/sql-pg pg --catalog
bun add -d drizzle-kit@1.0.0-rc.5-ab785fc @types/pg zod --catalog
bun add @alchemy.run/better-auth@latest better-auth@1.7.5 kysely --catalog

# web/
bun add @dueboard/api@workspace:*
bun add alchemy@latest @alchemy.run/cloudflare@latest effect @effect/platform-bun @effect/platform-node --catalog
bun add @effect/atom-react @tanstack/react-start @tanstack/react-router react react-dom better-auth@1.7.5 --catalog
bun add -d vite @vitejs/plugin-react @cloudflare/workers-types @types/react @types/react-dom zod --catalog
```

Most entries are caret ranges. A few versions have to match each other or are pinned by Alchemy:

- **`drizzle-orm` and `drizzle-kit`: `1.0.0-rc.5-ab785fc`.** Alchemy requires this exact version of both. Their `latest` tags point at the old `0.x` releases, so a plain `bun add drizzle-orm` installs the wrong one.
- **`better-auth`: `1.7.5`.** The version the Alchemy docs pin for `@alchemy.run/better-auth`. Give it explicitly when adding it to another workspace too, or `--catalog` resolves a newer one and overwrites the catalog entry.
- **`alchemy` and the `@alchemy.run/*` packages (`2.0.0-beta.84`).** They peer-depend on each other's exact release, so install and bump them together with `@latest`.
- **`effect` and the `@effect/*` packages (`4.0.6`).** Keep them on the same patch version. Alchemy `beta.84` needs `effect` `^4.0.5`.
- **`@tanstack/react-start` (`1.169.4`) and `@tanstack/react-router` (`1.170.46`).** `react-start` depends on exactly that `react-router` version. Any other version installs a second copy of the router, which breaks TanStack Start.

Bump each group together.

**Patched: `@alchemy.run/cloudflare@2.0.0-beta.84`** (`patches/`, listed under `patchedDependencies` in the root `package.json`). Under Bun, beta.84 starts the Vite dev server on Node with a loader file it doesn't publish, so `bun run dev:web` fails with `Cannot find module …/alchemy/bin/register-dev-mode.js` ([alchemy-run/alchemy#1868](https://github.com/alchemy-run/alchemy/issues/1868)). The patch is the upstream fix from [alchemy-run/alchemy#2525](https://github.com/alchemy-run/alchemy/pull/2525), unchanged; it's merged on `main` but not yet released. When upgrading past beta.84, check the release includes that PR, then delete the patch file and its `patchedDependencies` entry and run `bun install`.

Since `alchemy@2.0.0-beta.84`, the Cloudflare, Drizzle and Neon modules live in their own packages: import `@alchemy.run/cloudflare`, `@alchemy.run/drizzle` (and `@alchemy.run/drizzle/Postgres`) and `@alchemy.run/neon`, not `alchemy/Cloudflare`, `alchemy/Drizzle` or `alchemy/Neon`.

## Type-check and build

```bash
bun run build
```

This runs `tsc -b` over both workspaces through the project references. It also writes `api/lib/`. Outside Bun, imports of `@dueboard/api` resolve to `api/lib/` through the package's `exports`. That includes Vite bundling `web`, so build `api` before running `web`'s `dev` or `deploy`.

## Local development

Run each stack under `alchemy dev`, in two terminals, `api` first:

```bash
bun run dev:api
```

```bash
bun run dev:web
```

When `dev:web` is ready it prints `websiteUrl`: open that in the browser. Alchemy gives each local Worker its own port, so the `ApiWorker` gets `http://localhost:1337` and the site `http://localhost:1338`. Stop either with `Ctrl+C`.

`dev:web` runs `tsc -b` first, so `api/lib/` is current before Vite resolves `@dueboard/api/rpc`. After changing the RPC contract in `api/src/rpc.ts`, restart `dev:web` (or run `bun run build`) to pick it up.

**What runs where:**

- **Locally:** the `ApiWorker` runs in workerd, and the TanStack Start site runs on Vite's dev server with HMR. Both reload on file changes.
- **In the cloud:** Neon has no local emulator. `alchemy dev` creates a real Neon project and branch for your dev stage, and `Drizzle.Schema` writes migration files into `api/migrations/`; commit those.
- **No Hyperdrive in dev:** Alchemy doesn't create a Hyperdrive config under `alchemy dev`. The local `ApiWorker` connects straight to Neon's pooled endpoint (`dev: branch.pooledOrigin` in `api/src/database.ts`), so local calls are slower than deployed ones.
- **The `API` binding:** the local Website's binding to `ApiWorker` goes through Alchemy's machine-wide dev registry, which routes it to the locally running `ApiWorker`. That's why `api` must be started first and both must use the same stage.

**Stage:** `alchemy dev` uses the `dev_$USER` stage by default, separate from `alchemy deploy`'s `live_$USER`. Neither process tears down its cloud resources on exit. To remove them, run `alchemy destroy --stage dev_$USER` in `web`, then in `api`.

**Reading bindings in routes:** import `env` from `web/src/env.ts`, not from `cloudflare:workers`. TanStack Start's dev server evaluates route modules outside a Worker request, so a top-level `import { env } from "cloudflare:workers"` breaks in dev. `env.ts` wraps it in a Proxy that defers each lookup until a handler runs.

## Authentication

Better Auth runs inside the `ApiWorker` (`api/src/auth.ts`) on the same Neon branch, through the same Hyperdrive pool, as the todos. Alchemy creates its tables at deploy time (the migration connects to the branch directly) and generates a stable signing secret, kept in stack state.

**The flow:**

1. `/sign-in` → **Continue with Google**. Better Auth redirects to Google and back to `/api/auth/callback/google`.
2. A first sign-in creates the account and lands on `/onboarding` (`newUserCallbackURL`); a returning user lands on `/`.
3. `/onboarding` sets a unique username with Better Auth's [`username` plugin](https://www.better-auth.com/docs/plugins/username): 3–30 letters, numbers, `_` or `.`, compared case-insensitively.
4. The route guards (`beforeLoad`, through the `getSessionUser` server function) send anyone without a session to `/sign-in` and anyone without a username to `/onboarding`. The API applies the same rule: the `Authentication` RPC middleware rejects todo RPCs with `Unauthorized` and scopes every query to the current user.

**Hardening:**

- Session cookies are `Secure`, `HttpOnly` and `SameSite=Lax`, set explicitly because Workers have no `NODE_ENV` for Better Auth to infer production from.
- A signed copy of the session is cached in a cookie for 5 minutes, so route guards usually skip the database. Todo RPCs bypass that cache and check the session in the database, so a revoked session loses access to todos at once (a page may still render for up to 5 minutes).
- Google's OAuth tokens are encrypted at rest in the `account` table.
- `/api/auth/*` is rate limited per client IP (30 requests per minute) by Cloudflare's Rate Limiting binding (`AUTH_RATE_LIMIT` in `web/alchemy.run.ts`). Better Auth's own limiter is off, because behind the proxy it would see every request as coming from the web worker. Route guards read the session over the service binding and don't count against the limit.
- Todo RPCs are rate limited per user (120 per minute, `TODO_RATE_LIMIT` in `api/src/api.ts`), and todo text is 1–200 characters.
- Unexpected API errors (database or session lookup failures) are logged in the `ApiWorker` and reach the browser only as `Internal server error`.
- The client IP Better Auth records on each session comes from `cf-connecting-ip`, which Cloudflare sets and clients can't spoof.
- The username availability check (`/api/auth/is-username-available`) requires a session, so it can't be used to list accounts anonymously.
- Deploys require `AUTH_BASE_URL`, so Better Auth trusts only the website's origin for redirects, not every hostname that reaches the Worker.

**Set up Google** (once per environment):

1. In the [Google Cloud console](https://console.cloud.google.com/), open **Google Auth platform**: set up **Branding**, choose the **Audience** (add test users while the app is in testing), and keep **Data Access** to `openid`, `email` and `profile`.
2. Under **Clients → Create client**, create one **Web application** client and add both **Authorized redirect URIs**: `http://localhost:1338/api/auth/callback/google` for local dev, and `<websiteUrl>/api/auth/callback/google` for each deployed stage.
3. Copy `api/.env.example` to two gitignored files, and fill in the client's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in both:
   - `api/.env` for local dev. `bun run dev:api` reads it automatically. Leave `AUTH_BASE_URL` unset; Better Auth uses each request's origin.
   - `api/.env.live` for deploys, with `AUTH_BASE_URL` set to the website's https origin (no trailing slash). Deploy with `bun run deploy --env-file .env.live`.

   Alchemy binds these values into the `ApiWorker`; dev and deploy fail with a config error while the Google values are missing, and deploy also fails without `AUTH_BASE_URL`. So a deploy that forgets `--env-file` stops instead of using dev settings.

**A new stage** (e.g. a `pr-*` preview) gets its own random website URL, which only exists after `web` deploys, while `api` must deploy first. Deploy `api` with a placeholder `AUTH_BASE_URL`, deploy `web`, then set the printed URL, redeploy `api`, and add its callback URI to the Google client. A stage keeps its URL across later deploys unless it's destroyed or its Website is replaced.

Restart `dev:api` after changing `.env`. If the dev port changes, update the redirect URI to match.

## Hyperdrive

The `ApiWorker` reaches Neon through Cloudflare Hyperdrive, a connection pool at Cloudflare's edge, as in Alchemy's example. Workers can't keep a database connection open between requests, so without a pool every request opens a new Postgres connection: TCP, TLS and login, several round trips. Hyperdrive keeps those connections warm. Caching is disabled (`caching: { disabled: true }`), so writes show up immediately.

Hyperdrive needs the Cloudflare credential to include Hyperdrive permissions. Alchemy's Cloudflare OAuth login doesn't grant them, so this project uses an **API token** with **Hyperdrive: Edit**.

**Alternative without Hyperdrive:** `api/src/api.ts` keeps a commented `Neon.Connect` version, marked `Neon.Connect alternative`. It gives the Worker the branch's pooled connection string as a secret instead. It needs no Hyperdrive permission, but every request opens a new connection, which measured about 2 s per call from Asia to the Virginia database. To switch, swap the marked lines in `api.ts` (and its imports). Better Auth still connects through Hyperdrive (`api/src/auth.ts`); to drop Hyperdrive entirely, also give it the `@alchemy.run/better-auth/Neon` layer, then remove the `hd` line and the `hyperdriveId` output in `api/alchemy.run.ts` and `api/src/Stack.ts`.

## Deploy

Credentials for Cloudflare and Neon are stored in Alchemy profiles. Cloudflare uses an API token (Alchemy's OAuth login can't grant the Hyperdrive permission). Set it up with `bunx alchemy profile edit --add Cloudflare` → API Token, and Neon with `--add Neon`. The first deploy prompts for any that are missing.

Deploy `api` first. The web stack binds to its deployed `ApiWorker`, and its plan fails with `InvalidReferenceError` if `api` isn't deployed to the same stage:

```bash
cd api && bun run deploy
```

```bash
cd web && bun run deploy
```

To tear down, destroy them in the reverse order: `web` first, then `api`.

Each workspace also has these scripts: `dev` (`alchemy dev`, which the root `dev:api` and `dev:web` scripts call), `destroy`, `logs`, `tail` and `test`. `web` also has `build` and `preview`, which run Vite directly.
